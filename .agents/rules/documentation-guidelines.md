# Arranger Documentation & Sample Code Guidelines

本ガイドラインは、Arranger プロジェクトにおける README、公式ドキュメント、サンプルコード、およびビジュアルアセット（画像・GIF）の品質と保守性に関する原則を定めます。

---

## 1. README・ドキュメントのキュレーション原則 (Curated Presentation)

- **[推奨されるドキュメント]:**
  - **価値中心のグループ化と厳選**: アピールしたい主要機能を厳選し、単なる機能の機械的羅列ではなく、開発者にどのような価値・体験をもたらすかを明瞭に説明する。
  - **概念の包含関係（Conceptual Hierarchy）の遵守**: 一般概念と具象機能の親子関係を自然に構造化する（例: `Interactive Spans & Tap Handling` という一般機能のセクション内に `Hyperlinks & URL Detection` の説明を配置する）。
  - **折りたたみタグによる一覧性の確保**: 長大なコードブロック（サンプル実装やセットアップ手順）は `<details><summary>View code example</summary>...</details>` を用いて適切に折りたたみ、ドキュメント全体の見通しを維持する。
- **[拒否されるアンチパターン]:**
  - 新機能を追加するたびに、既存セクションとの関連性を考慮せず箇条書きの末尾に単に足し合わせるカタログ的な記述。
  - ドキュメント冒頭で長大なボイラープレートコードを展開し、ファーストビューを阻害すること。

---

## 2. サンプルコードの可読性と設計 (Sample Code Quality)

- **[推奨されるサンプルコード]:**
  - **コンポーネントの責務分割**: 1つの Composable 関数にUI構築、状態管理、イベントハンドリングを詰め込まず、見通しの良い小さなコンポーネントに分割する。
  - **パラメータラベル（Parameter Labels）の明記**: 引数の意味を初見で理解できるよう、主要な引数にはパラメータラベルを付与する（例: `listOf(Item(id = 1, name = "Arranger"))`）。
- **[拒否されるアンチパターン]:**
  - 1関数が数百行に及ぶスパゲティなサンプルコード。
  - 内部実装の都合が漏れ出し、ライブラリ利用者の参考にならない複雑すぎる状態管理。

---

## 3. ビジュアルアセットの撮影品質 (Visual Asset Standards)

- **[推奨される撮影手順]:**
  - **クリーンなキャプチャ**: エミュレータや実機でスクリーンショットやデモGIFを撮影する際は、IME入力ツールバー、ソフトウェアキーボード、デバッグオーバーレイ等の余計なシステムUIが写り込まないよう環境を整理して撮影する。
  - **アセットパスの整合性確認**: READMEに埋め込む画像パス（例: `docs/images/feature-demo.gif`）と実際のアセットファイル名が正確に一致していることを確認する。
- **[拒否されるアンチパターン]:**
  - 入力中の予測変換候補バーやキーボードが画面の大半を覆っている不完全なスクリーンショット。
  - 過去の古い機能のデモ画像や関係のないGIFを流用すること。

---

## 4. OSS公開言語ポリシー (Strict English Policy)

- **[標準規範]:**
  - 公開されるすべてのドキュメント（README、KDoc、コード内コメント、コミットメッセージ、PRタイトル・本文、GitHub Issueへの返答）は**すべて英語**で記述する。
  - ユーザーとの対話やローカルのAI設定（`.agents/` 内のスキル・ルール定義）は日本語を使用するが、リポジトリに公開されるプロダクトコード・ドキュメントに日本語を混入させてはならない。
