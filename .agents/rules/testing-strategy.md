# Arranger Testing Strategy Principles

## 1. 推奨されるテストの構造とパターン
- **[人間が求める理想のテストコード]:** 
  - 厳格な **AAA (Arrange-Act-Assert)** パターンの遵守。データの準備、実行、検証を明確に分離する。
  - テスト関数名は英語のバッククォート（`` ` ``）で囲み、振る舞いを明確に表す完全な英文（例: `` `editAll with empty ranges is a no-op` ``）とする。
  - ロジックの検証だけでなく、Compose UIの振る舞いに対しては **Roborazzi** を用いたスクリーンショットテスト（`captureRoboImage` / `captureRoboGif`）を実施し、ビジュアルの回帰を検知する。
- **[拒否されるアンチパターン]:** 
  - Arrange・Act・Assertが入り乱れ、何が前提で何を検証しているか不明瞭なスパゲティテスト。
  - UIコンポーネントに対するアサーションにおいて、スクリーンショットによる視覚的検証を怠り、内部状態のプロパティだけを見てUIが正しく描画されているとみなすこと。

## 2. State・UIロジックの検証鉄則
- **[人間が求める理想の検証]:** 
  - `RichTextState` 等のUI状態は、純粋なKotlinロジックとして検証するだけでなく、必ずUI（`RichTextEditor`）に注入した際のエンドツーエンドの振る舞いとしても検証する。
  - エッジケース（空文字の入力、空の範囲の編集、連続した改行、ネストされたリストの中間での改行など）を意図的に作り出し、システムがクラッシュせず想定通りにフォールバック（no-opなど）するかをテストする。
- **[拒否されるアンチパターン]:** 
  - 正常系（ハッピーパス）が1つ通るだけの薄いテスト。
  - リストのネストや境界値など、ユーザー操作によって頻繁に発生しうる複雑なエッジケースを「実装が面倒だから」という理由で省くこと。

## 3. テストのクオリティとカプセル化
- **[人間が求める理想の検証]:** 
  - **モック（Mock）の利用を極力避ける。** MockitoやMockKなどのモックライブラリに依存せず、本物の `RichTextState`、`RichString`、本物の Compose UI 環境（RobolectricTestRunner + ComposeRule）を用いて、実際の動作に限りなく近い状態でテストを行う。
  - `Kotest` のマッチャー（`shouldBe`, `shouldBeEmpty`）を活用し、検証コード自体が自然言語のように読める表現力豊かなアサーションを記述する。
- **[拒否されるアンチパターン]:** 
  - 内部実装（privateな状態）を強引にリフレクション等で読み取ってテストするような、カプセル化を破壊するアプローチ。
  - 過度なモック化により「モックの振る舞いをテストしているだけ」になり、実際の連携時のバグを見逃してしまうテスト設計。

## 4. KMP（Kotlin Multiplatform）環境におけるテスト責務
- **[人間が求める理想の検証]:** 
  - ビジネスロジック（`RichTextState` の状態遷移、`RichString` の操作ロジックなど）に対する単体テストは、必ず `commonTest` ソースセットに配置する。これにより、JVM、iOS、WasmJsなど全ターゲットで同一のテストが走り、プラットフォームごとの差異（特にWasm/JS環境での型の振る舞いなど）がないことを保証する。
- **[現状の制約とアンチパターン]:** 
  - KMPの強みを生かさず、Android向けの `androidTest` や `test` など特定のプラットフォームに依存した場所に共通ロジックのテストを置いてしまうこと。

## 5. 今後の標準となる先進的なテスト戦略 (Advanced Testing Strategies)

これからのArrangerの開発において、これまでの限界を超えて積極的に導入・徹底すべき高度なテスト戦略です。エージェントは以下の観点を意識し、実装の機会があれば能動的にテストを作成してください。

- **クロスプラットフォームでのUI・レンダリング検証**
  現在はJVM(Robolectric)上のRoborazziがメインですが、Compose Multiplatformの機能拡充に合わせて、iOS固有のフォント描画やWasmのCanvas描画、OS特有のIME入力との相性問題など、実ターゲット環境でのE2E/ビジュアル検証の導入を常に検討・実施すること。
- **アクセシビリティ（a11y）とセマンティクスの検証**
  リッチテキスト（太字、見出し、リストなど）が視覚的に正しいだけでなく、`onNodeWithText`、`SemanticsActions`、`ContentDescription` 等を用いて、スクリーンリーダーなどからも正しい構造（Semantics Tree）として読み取れるかどうかのテストを必ず追加すること。
- **パフォーマンス（Microbenchmark）の自動計測**
  `editAll` のような重い処理や長文入力において、パフォーマンスの劣化（リグレッション）を防ぐため、`kotlinx.benchmark` 等を用いた定量的なベンチマークテストの作成・実行を積極的に行うこと。
