# Arranger Core Architecture Principles

## 1. 状態管理とデータフローの鉄則
- **[人間が求める理想の実装]:** 
  状態管理は単一情報源（Single Source of Truth）を徹底し、単方向データフロー（UDF）を守る。`RichTextState`のように状態（State）そのものは`@Stable`として提供し、外部からの変更は特定のトランザクション（`edit { }` DSLなど）を通じた純粋な更新ロジックに限定する。また、一時的なUI状態（例：`typingAttributes`）は文字入力時に自動クリアされるなど、副作用を厳格に管理する。
- **[拒否されるアンチパターン]:** 
  コンポーネント内やViewModel内で状態のミュータブルなリストを直接書き換えたり、内部実装（`spans`の生リストなど）を外部にパブリックプロパティとして露出させる実装。副作用を伴う更新をUIコンポーネント（Composable）内で直接行うこと。

## 2. UIフレームワーク・パフォーマンスの制約
- **[人間が求める理想の実装]:** 
  Jetpack Composeの思想に完全に従い、無駄な再コンポジションを防ぐために`derivedStateOf`を適切に活用する。不要なオブジェクトアロケーションやO(N*M)の計算を避けるため、最適化されたアルゴリズムを採用する。
- **[拒否されるアンチパターン]:** 
  頻繁に更新されるプロパティ（例：`selection`や`currentAttributes`）の計算において、都度不要なループ処理や全スキャンのフィルタリングを行いメモリを圧迫・UIスレッドをブロックする実装。

## 3. APIデザイン・命名規則・カプセル化
- **[人間が求める理想の実装]:** 
  APIは呼び出し側（Compose/SwiftUI）から見て直感的で宣言的であること。引数渡しは必ず名前付き引数（ラベル付き引数）を使用し（自明な場合を除く）、コメントやコードドキュメントは英語で統一する。公式のCompose API Guidelinesに準拠する。
- **[拒否されるアンチパターン]:** 
  ワイルドカード(`*`)を使用したimportの利用、意味が不明瞭な引数の省略、内部的なロジックをクラスのpublicメソッドとして無秩序に公開すること。また、プラットフォーム固有の処理（iOS限定の問題対応など）のために共通層（Common）の美しい設計を歪めること。

## 4. 型安全（Type-Safe）なライブラリ設計
- **[人間が求める理想の実装]:** 
  属性（Attributes）の管理は単なる文字列キーのMapではなく、`AttributeKey<T>` インターフェースを用いた厳格な型安全性を保証する。各属性キーは `defaultValue` を持ち、値の型 `T` がコンパイラによって検証されることで、開発者の実行時エラーを防ぐ。
- **[拒否されるアンチパターン]:** 
  `Map<String, Any>` のような型情報が喪失するデータ構造を公開APIとして用いることや、利用側でダウンキャスト（`as T`）を強制し、型チェックの責任を押し付ける設計。

## 5. 宣言的UI（SwiftUI/Compose）のパラダイム適用
- **[人間が求める理想の実装]:** 
  SwiftUIの `@State` / `@Binding` や ViewModifier のような宣言的なアプローチを採用する。UIコンポーネント（`RichTextEditor`）は状態を持たず、渡された `RichTextState` を純粋に描画する。また、見た目のカスタマイズは `AttributeStyleResolver` を用いて、SwiftUIのEnvironmentやModifierのように宣言的かつ柔軟に注入できるようにする。
- **[拒否されるアンチパターン]:** 
  UIコンポーネントの内部で描画スタイル（色やフォントサイズなど）をハードコードしたり、命令的（Imperative）にViewのプロパティを直接操作するようなレガシーな設計。

## 6. KMP（Kotlin Multiplatform）としての責務分離
- **[人間が求める理想の実装]:** 
  リッチテキストの「データ構造（モデル）」「状態管理」「属性のロジック」はすべて `commonMain`（プラットフォーム非依存）に配置する。プラットフォーム固有のUI描画への依存は最小限に留め、ビジネスロジックはピュアなKotlinで記述する。
- **[拒否されるアンチパターン]:** 
  テキストの計算ロジックや状態管理に、特定のプラットフォーム（例えばAndroidの `SpannableString` や iOSの `NSAttributedString`）の概念を安易に持ち込み、コードの共通化を阻害すること。
